**Status:** proposal, for approval. Nothing here is implemented.
**Patches:** the v3 architecture set, in place. Every affected document is revised
rather than superseded; this file is the record of *what changed and why*, so the
diff can be reviewed as a set of decisions rather than as a wall of prose.

the consistency check verified that ten documents *agreed with each other*, and

## 1 · The security fix, and how it got past three reviews

### What was wrong

`site/supabase/v3/03_achievements.sql`, as drafted in v3:

```sql
create policy "own verification insert" on public.achievement_verifications
  for insert to authenticated with check (auth.uid() = user_id);
```

`auth.uid() = user_id` proves the row is *about* the caller. It proves nothing
about whether the caller earned what the row claims. Any signed-in person could
insert a row naming any badge in the public catalogue and immediately hold a
public, crawlable, indexable page — with an AdelTechTalks-branded share card —
asserting they had earned it. The site's own branding would be vouching for it.

### Why it survived review

Every sentence around it was true.

- The table *is* a deliberate public projection.
- The row *does* hold nothing sensitive — a name, a badge, a date.
- Sharing *is* the user's own choice.
- `shares` *did* work exactly this way in v2.x, and worked fine.

That last one is where it came from, and it is where the reasoning broke. In v2.x,
`shares` was written by a client that had already written its own `badges` row
client-side. The entire loop was self-asserted, and that was acceptable because a
Playground track badge asserted almost nothing — "I clicked through a quiz".

v3 makes badges mean something: earned against server-scored challenges, tied to
course completion, tied to XP thresholds, rendered with the word *verified*.
**The moment a badge means something, the ability to self-issue one stops being
harmless.** The v2.x precedent was carried across without re-asking whether its
premise still held. The consistency check then confirmed that the migration and
the gamification document told the same story, which they did.

The lesson, written into the Security Model as the new policy test: *"own rows
only"* is not a security property. The question is **"if a client wrote this row
itself, what could it then obtain?"**

### The fix

1. **No insert, update or delete policy on `achievement_verifications`, for any
   role**, and the grants revoked as well, so a policy added by accident still
   cannot write. The only policy is the public `select`, scoped `revoked_at is
   null`.
2. **`POST /api/achievements/publish`** — authenticate, rate-limit, prove
   ownership against `user_badges` / `enrollments` / `challenge_attempts`, derive
   every public field server-side, generate the id server-side, insert. It
   **refuses** a request carrying `user_id`, `display_name`, `earned_at`, `score`,
   `level_key`, `total_xp` or a verification id — refuses with a 400, rather than
   stripping them silently.
3. **`POST /api/achievements/unpublish`** — a soft revoke scoped to the session's
   user. The id survives, so re-publishing restores the same URL instead of
   orphaning every link already posted. The v3 draft deleted the row.
4. **Administrative revoke** exists, has no UI, and cannot be undone by the user.
5. **Display names are sanitised server-side** and an account without one cannot
   publish — it never falls back to the email local part.

Full contract, including the hostile-client table that becomes a CI suite:
`V3_API_SURFACE.md` §2.

### What else the same test caught

Applying *"what could a client obtain by writing this?"* to the whole migration
set found three more:

- **`playground_track_badges`** — client-writable, and it *fed* `user_badges`,
  which is what the publish endpoint accepts as proof. A complete escalation
  chain, entirely inside the v3 set. → change 2.
- **`lesson_progress`** — client-writable, and lesson completion drives
  `enrollments.completed_at`, which is proof of a course achievement. → now
  server-written.
- **"save a first prompt · 5 XP"** — a server-issued award whose evidence was a
  client-written row. → the award is removed; `saved_prompts` stays a bookmark
  and stays client-writable, because a bookmark confers nothing.

After the patch, exactly two tables in the whole schema accept a client write:
`saved_prompts` and `subscribers`. A CI policy audit asserts that list.

## 2 · Retiring the legacy path *(change 2)*

The v3 set said `playground_track_badges` "becomes read-only legacy" and left it
`for all to authenticated`. That is an intention, not a migration.

Migration 07 gives it three stages with verifiable preconditions:

| stage | when | what changes |
|---|---|---|
| 1 | Phase 0, with migration 02 | both legacy tables become `select`-only; grants revoked; the 02 backfill is sealed by a marker so it can never re-run and can never again feed `user_badges` |
| 2 | Phase 2 | the shim endpoints are deleted; nothing writes the tables at all |
| 3 | Phase 4, ≥90 days later | the tables move to an `archive` schema, out of `public` |

**Archived, not dropped.** They are the provenance of every backfilled
`user_badges` row, and those rows can become public verified achievements. A
verified achievement whose origin has been deleted is one nobody can audit.

**The cost, stated plainly:** stage 1 breaks the live v2.x Playground unless the
server-mediated write path ships in the same deploy. So Phase 0 is no longer
"nothing user-visible ships" — it ships two shim endpoints that perform the
Playground's existing writes from the server. Nothing moves on screen; the
authority moves. That is a real amendment to the v3 phase plan and it is recorded
in `V3_IMPLEMENTATION_PLAN.md` §4.

## 3 · The product corrections *(changes 4–8)*

### BUILD → PLAY → LEARN → SHIP

The v3 draft ran *Learn → Play → Build → Ship*. That is the order a curriculum
designer writes; it is not the order a stranger experiences. Someone arrives
because Adel builds things, the first interesting thing they can do is try one,
and only then does a reading list mean anything.

The homepage is regrouped into four acts and **Prompt Arena moves from position 5
to position 4** — above the reading list rather than below it. Each act gets one
motion register (drawn / responsive / calm / settling) so the structure is legible
without a word of explanation, and PLAY deliberately has *no* entrance motion:
after two acts of things arriving, the act where the visitor acts is still until
they do.

The Hero's primary action changes from **Start Learning** to **Try a challenge**.
The first is a commitment to a reading list; the second is a thirty-second act
with a result at the end of it.

### Playground is a product

Prompt Arena opens with **nine challenges** — three Choose, three Repair, three
Create — or `/playground/` does not open. This is a publication gate of exactly
the kind v2.x already enforces on Gear photographs and Build screenshots: the
engine, scoring, XP, badge evaluation and routes all ship complete; the route
waits for content. A half-full Arena is not shipped and then filled.

The architecture does not assume prompting. Future experiences bring their own
challenges, rubric and dimensions; they do not bring their own scoring engine, XP
path or achievement table.

**And Create had to be corrected.** Create is self-assessed at foundation — the
learner grades their attempt against a worked model answer, which is honest and is
most of the value. What the v3 draft never said is what that score is *worth*: it
is worth completion XP and nothing else. It cannot satisfy a score-gated badge and
it cannot be published as a verified achievement. Consequence:
**`prompt-architect` ships visible and locked** until Phase 4 brings model-assisted
scoring, rather than shipping as a badge that quietly grades itself.

### One achievement infrastructure

`achievement_verifications` is generalised from a badge to a `subject_type` —
`badge`, `course` or `challenge` — with one route, one card generator and one
ownership check per kind. Three separate achievement systems would be three
separate chances to get the ownership check wrong, and the one that got it wrong
would be the one nobody reviewed twice.

Build achievements (Phase 4) are deliberately **not** a fourth kind. They are
badges with `user_badges.source_type = 'build'`, so they inherit an ownership
check that already exists rather than needing one invented at the call site.

### The share card

1200×630, generated on demand from the verification row, edge-cached by id plus a
version token derived from `published_at` so a re-publish busts the cache.
Branding, achievement art, the snapshotted display name, the verification line, a
CTA. Score only where consented. **Never** an email, another member, a rank, or a
count. Arabic cards render in the snapshot language and fall back to the **English
title** rather than machine-translating — the authored-Arabic rule applies to
generated images exactly as it applies to pages.

It is generated by the site and is **not** a Canva template. A share card that can
be typed into is a share card that can claim anything.

### The contextual acquisition loop

"Join AdelTechTalks" on a page reached from a share asks a stranger to commit
before they have any reason to. Replaced with a CTA that names what they just
looked at: **"Think you can beat 94?"** on a challenge achievement, "See what this
course teaches" on a course one, "Earn this badge" on a badge one, and after an
anonymous attempt, *"You scored 84. Create a free account to keep it."*

The rule underneath: **do the thing → see your result → then the account is how
you keep it.** The homepage's Join Free section is the only place that asks first.

### Honest launch state

Three named states, because conflating them is how "coming soon" becomes a lie:

- **Live** — real, works.
- **Preview** — designed, named, genuinely committed, not open. A quiet,
  **non-interactive** card that states its *condition*, not an invented date. Never
  above the fold, at most one per section, and a section that would be all preview
  is Absent instead.
- **Absent** — the section collapses. No placeholder, no skeleton. *A skeleton
  shimmer is a looping animation claiming something is loading.*

At launch: Prompt Arena is Live; other experiences are Preview; Courses and
Resources are Absent; the homepage achievements wall is Absent until three real
verifications exist and **is never seeded**. No counts, no ranks, no "X learners".

## 4 · The commerce hardening *(no defect, stated anyway)*

The v3 commerce design was already webhook-authoritative. Three things are now
stated explicitly, because "we all know that" is how they get lost:

- `/api/checkout` accepts a `product_key` and **nothing else about money** — no
  amount, no currency, no `price_id`. A client-supplied price is a discount the
  customer wrote themselves.
- **No endpoint reads `session_id` from a redirect and grants anything.** The
  success page polls the entitlement resolver.
- Stripe secrets are **Cloudflare secret bindings** — not `vars`, never
  `PUBLIC_`-prefixed, never in a module reachable from a client island. The CI
  grep matches secret *values*, not binding *names*.

## 6 · What is still open after this patch

Unchanged from v3 and still blocking a release rather than an implementation:

- **Authored Arabic** for every new string, marked `‹author›`. Level names, nav
  labels, Preview-card copy, challenge copy, achievement titles.
- **Real content**: project screenshots, the nine Prompt Arena challenges, course
  material.
- **Confirmation** that `/gear/*` should 301 to `/projects/` rather than to Learn.

New with this patch:

- **The nine-challenge launch gate is a commitment to write nine challenges.** It
  is the single largest content dependency in Phase 2, and the honest options are
  to write them or to move Playground to Phase 3 — not to open the Arena with
  three.
- **`prompt-architect` is locked until Phase 4.** If a score-gated prompting badge
  is needed at launch, it has to be gated on a Choose or Repair challenge, which
  the server can grade.
- **Whether the homepage achievements wall is worth building** before there is
  anything real to put in it. It is specified and it will be Absent at launch; the
  alternative is to defer the component to Phase 4.
